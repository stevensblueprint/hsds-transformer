# Blueprint research

1. State the question and the decision it informs. Read the applicable repository guidance, current README, relevant implementation, tests, and configuration. Record the revision; start with the narrowest relevant path rather than loading the whole repository.
2. Trace each material claim to a file and revision, an observed check, or a dated primary source. For external format or library questions, consult the authoritative specification or version-matched documentation when accessible. Repository behavior and specification requirements are separate claims.
3. Resolve disagreements using evidence appropriate to the question: executable configuration for available commands, implementation plus behavior checks for actual results, and the supplied requirement for desired behavior. Flag missing access or unresolved conflicts rather than filling gaps with assumptions.
4. Return the answer with supporting links, alternatives only when they affect the decision, and the smallest next check for remaining uncertainty. Label observations, source-derived conclusions, hypotheses, and recommendations distinctly. Do not treat a passing static check as runtime evidence.

Use `$codebase-tour` for navigation alone and `$blueprint-knowledge` when asked to
preserve the result in an existing document. Research itself grants no permission
to edit external documents, publish comments, or change the application. Use only
authorized project sources; do not import unrelated workplace material.
